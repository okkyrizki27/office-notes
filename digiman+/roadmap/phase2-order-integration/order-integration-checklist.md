# Order Integration — Requirement Discussion Checklist

Framework diskusi requirement Phase 2 Order Integration, dipecah jadi beberapa topik supaya diskusi tidak melebar dari konteks. Centang langsung di tempat kalau topik sudah dibahas tuntas & clear — bukan daily/outstanding task list, jadi tidak perlu dipindah ke section terpisah.

Urutan dikelompokkan jadi 6 fase berdasarkan dependency — fase awal menentukan scope & aktor, masuk ke jantung data model, lalu proses/workflow, integrasi, dan terakhir dashboard (baca dari hasil akhir semua keputusan sebelumnya).

## Fase C — Data Model
*Jantung diskusi, paling banyak keputusan*

- [x] **4. Offline behavior create Finding/Order** — ada draft state (simpan progress tanpa submit final, publish ke topic cuma saat submit). **Resolved (2026-08-17):** hubungan dengan offline-first pattern Phase 1 (2 sumbu independen — transport vs business-state, compose bukan duplikat, termasuk skenario create→draft→submit yang 100% offline); timing correlation check (independen dari draft/submit, live query berbasis field client-side); count badge (cuma hitung submitted, draft tidak ikut); correlation check offline (cache kandidat lokal, trade-off staleness diterima, ditutupi Planner approval); siapa yang bisa edit + offline (`IAMS_Mobile_DefectCrack_Edit`/`_Edit_Others`); race condition 2 device edit bersamaan (last edit-time menang, bukan last-arrival, sync tetap sukses + pesan response API "ada update terbaru" — bukan reject/requeue). Residual kecil (implementasi, bukan desain): detail sync-down interval/trigger cache kandidat offline. Detail: [Poin 4](order-integration.md#poin-4-offline-behavior--draft-state-2026-08-15).
- [x] **5. Data flow of defect/crack** (Defect, Monitored Crack, Crack) — Crack Order Lifecycle, mekanisme save-execution-first→publish→consume, eMOL vehicle-approval untuk reuse, skema `TaskPersonalizedFindingMaterial`/Order Type/Activity Type — semua sudah didesain lengkap. **Crack journey confirmed sama dengan Defect journey** (2026-08-15). **Resolved (2026-08-17):** `Monitor`/`Repair Required` TIDAK mapping/mempengaruhi `PriorityCode` maupun `IsImmediateExecutable` — keduanya independen, sistem sengaja tidak membatasi kombinasi (kondisi lapangan dinamis). **Gap ditemukan & resolved (2026-08-17):** `CrackIdentified` ternyata tidak punya tujuan di `maintenance-order` — Planner tidak akan bisa lihat Crack Description/Length saat approve. Fix: tabel baru `MechanicOrderCrackIdentified`, mirror `CrackIdentified`, FK `MechanicOrderListId`. Backfill TIDAK perlu (confirmed — belum pernah ada eMOL historis dari Crack finding). **Open item besar resolved (2026-08-17):** edit setelah publish/approval triggered — lock begitu tier pertama Order-approval chain memproses (bukan tier akhir), butuh topic arah balik baru `maintenance-order`→`maintenance-execution`. **Resolved (2026-08-17) — evidence/foto carry-over:** bukan gap — `TaskPersonalizedEvidence`→`MechanicOrderEvidence` (`Name`/`ContentAddress`) **sudah confirmed live di skema real** (bukan proposal), pola existing yang sudah jalan buat eMOL Inspection hari ini, consumer Phase 2 tinggal replikasi. Sisa open item: konfirmasi multi-Finding dalam 1 pertanyaan (Tab Finding #1/#2) tetap independen jadi eMOL masing-masing. **Ditambahkan (2026-08-17):** [Data Propagation Mapping](order-integration.md#poin-5-data-flow-defect-dan-crack) — konsolidasi semua field mapping `maintenance-execution`→`maintenance-order` (7 tabel: List, Detail, CrackIdentified, Material, PoolingMOItem, Evidence, + arah balik) jadi 1 acuan developer, tanda 🆕/✅ per kolom/tabel. Lihat [Poin 5](order-integration.md#poin-5-data-flow-defect-dan-crack).
- [x] **6. Duplicate/correlation handling** — correlation key = Asset + Component + SubComponent + DamageCode; sistem suggest kandidat, human (siapapun yang kerjakan form) yang pilih & validasi; Order lama tidak diubah, cukup di-close & sync SAP. **Resolved (2026-08-17):** reuse TIDAK exclusive — 1 Order boleh direuse berkali-kali oleh banyak Finding bersamaan, tidak jadi "terpakai" begitu di-reuse 1x. Invalid cuma kalau sudah `MONo` dari SAP + sudah masuk `BacklogExecutionList` (kriteria sama dengan filter `MOOpen` minus `BacklogExecutionList` yang sudah ada). **Resolved (2026-08-17) — edge case stale candidate:** validasi ulang `ReuseOrderNumber` di titik submit final (bukan cuma pas "Check Existing" awal) pakai kriteria yang sama — kalau sudah invalid, submit di-block khusus bagian reuse, user diarahkan re-run search atau lanjut Order baru. Berlaku juga tiap edit yang mengubah `ReuseOrderNumber`. Detail: [Poin 6](order-integration.md#poin-6-duplicate-atau-correlation-handling).
- [x] **7. Status Draft/Submitted ditampilkan per-Tab Finding (di Tab selector + di konten tab aktif), bukan 1 status level-layar. Sisa open item: beda dari Poin 10 (Reject/rework) — ini koreksi mandiri mechanic, bukan penolakan approver. Detail: [Poin 7](order-integration.md#poin-7-editability-window-sebelum-approval).
- [x] **8. ## Fase D — Proses/Workflow

- [x] **9. Approval of Defect/Crack** — Form approval & Order approval confirmed 2 jalur independen, bukan nested. **Catatan terminologi (2026-08-17):** "Foreman/Supervisor"/"Planner" adalah shorthand tingkat akhir approval chain yang configurable (Form: Supervisor; Order: kemungkinan Supervisor→Planner, 2 tingkat — perlu konfirmasi BPO), desain tidak bergantung jumlah tingkat. **Reversed (2026-08-16):** SEMUA kombinasi reuse (Yes maupun No) sekarang lewat Order approval (eMOL vehicle-approval) — sebelumnya `No`+reuse skip Order-approval, dibalik karena keputusan reuse/execute-now/material harus divalidasi supervisor/planner, bukan self-declared mechanic. Bedanya cuma post-approval action: `Yes` trigger `BacklogExecutionList`, `No` cuma jadi record approved tanpa aksi lanjutan. **Resolved (2026-08-17) — User Journey Approval Order (sebelumnya "sisa besar"):** 1 Finding=1 Order=1 approval; layar view-only + tombol Edit (pola sama Poin 7); approver bisa edit SEMUA field mechanic di level approval manapun (termasuk `ReuseOrderNumber`, kena validasi stale-candidate yang sama); mode Edit ada Cancel/Discard+Save, keduanya balik ke view lalu Approve terpisah; update balik ke `maintenance-execution` tiap aksi Approve lewat topic yang sama dengan flag lock (diperluas, dinamai general). Race condition mechanic-vs-approver: **approver selalu menang**. **Gap #3 (Override IsImmediateExecutable) resolved** — efek ganda (catatan final + pengaruh routing) sekaligus, bukan pilih salah satu. **visibility resolved sebagian** — `IsImmediateExecutable` dibawa ke `MechanicOrderDetail`/View Detail Order. **Deferred (2026-08-17) ke next MVP:** mekanisme bukti/evidence pasca-perbaikan buat verifikasi klaim eksekusi (gap #2) — Phase 2 andalkan laporan self-declared mechanic apa adanya; UI indikator post-hoc untuk Order yang sudah dieksekusi non-blocking — Phase 2 pakai layar view/edit standar tanpa indikator khusus. Sisa open (bukan defer, genuinely butuh info eksternal): role detail tier approval (Fase B, perlu konfirmasi BPO client). Lihat [Poin 9](order-integration.md#poin-9-approval-flow).
- [x] **10. Reject/rework flow** — **Deferred (2026-08-17):** fitur reject **belum ada** di approval Phase 2 ini (binary pending→approved saja, tidak ada tombol reject) — di-defer ke next MVP, bukan gap Phase 2. 2 fakta sudah diputuskan buat referensi nanti: rejected → tidak sync SAP/`PoolingMOItem`, dan tidak bisa resubmit (terminal). Detail lain (siapa bisa reject, UI, alasan disimpan di mana) genuinely belum dibahas, next MVP. Icon state "Rejected" ikut tetap deferred (tidak ada trigger di Phase 2). Detail: [Poin 10](order-integration.md#poin-10-rejectrework-flow).

**Out of scope (2026-08-17):** Notification (siapa di-notify kapan, push/in-app/email) — dihapus dari scope Phase 2 ini, belum ada mekanisme notifikasi apapun di app hari ini.
