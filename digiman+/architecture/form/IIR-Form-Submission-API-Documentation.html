1. Overview & Perubahan dari v0.4

Integrasi ini mengirimkan data hasil pengisian form self-service di Digiman+ — form yang diisi lewat menu mobile "Form Submission" (bukan form inspeksi/PM/BD corrective terjadwal) — ke sistem eksternal.

Model integrasinya adalah push: setiap kali sebuah form disubmit, Digiman+ mengirim satu HTTP POST berisi data submission lengkap ke endpoint yang kalian sediakan. Tidak ada polling, tidak ada penjadwalan dari sisi kalian — data datang sendiri, mendekati real-time.

Setiap kiriman mencakup metadata (kategori form, site, equipment, waktu submit) dan seluruh jawaban form terstruktur per tab & section, termasuk referensi ke foto.

1.1 Ringkasan Perubahan dari Draft v0.4

Breaking — arah integrasi dibalik, v0.4 tidak lagi berlaku
  • Model berubah dari pull menjadi push. Di v0.4, sistem kalian yang memanggil endpoint Digiman+ secara berkala. Sekarang Digiman+ yang memanggil endpoint kalian setiap ada submission baru.
  • Seluruh endpoint polling dibatalkan — GET /form-submissions (list) dan GET /form-submissions/{id} (single-fetch) tidak akan dikembangkan. Semua yang terkait di v0.4 ikut gugur: pagination, filter dateFrom/dateTo, parameter formSubGroup/siteCode/equipmentNumber, dan rate limit endpoint data.
  • Kalian perlu menyediakan 1 endpoint baru untuk menerima kiriman — lihat bagian 3. Ini pekerjaan baru di sisi kalian yang tidak ada di v0.4.
  • Payload dikirim satuan — satu POST = satu submission. Envelope submissions[] beserta totalRecords/page/pageSize/hasMore dihapus; isi objek submission yang dulu ada di dalam array sekarang menjadi objek root.
  • Akses foto berubah total: photos[].url sekarang berisi URL Azure Blob Storage langsung, bukan lagi link ke endpoint proxy Digiman+. Untuk mengambil isinya, kalian minta SAS token lebih dulu lewat endpoint baru — lihat bagian 5.
  • Field baru valueCode pada jawaban checklist — lihat 4.4. Disediakan supaya logic kalian tidak bergantung pada teks tampilan yang bisa berubah.
Tetap sama seperti v0.4
  • Struktur isi payload per submission (tabs → sections → answers) tidak berubah, kecuali tambahan valueCode dan perubahan isi photos[].url.
  • Autentikasi ke Digiman+ tetap API Key + IP whitelist — tapi sekarang hanya dipakai untuk endpoint SAS token (bagian 5 & 7).
  • Perbedaan makna submittedAt vs syncAt tetap berlaku dan tetap penting — lihat 4.2.

1.2 Cakupan Awal

Untuk tahap pertama, yang dikirim hanya kategori form IIR, dari seluruh site. Mekanismenya sendiri sudah generik untuk kategori form lain — penambahan kategori di kemudian hari cukup lewat konfigurasi di sisi Digiman+, tanpa perubahan kode di sisi kalian, selama endpoint penerima kalian memperlakukan tabs/sections/answers secara dinamis (lihat 4.3).

2. Alur Integrasi

1
Inspector — Mobile Digiman+
Inspector menyelesaikan dan submit form di aplikasi mobile. Bisa dilakukan dalam kondisi offline.
2
Digiman+ — Internal
Begitu data submission sampai di server Digiman+, sistem menyusun payload lengkap (metadata + seluruh jawaban + referensi foto) dan mengantrikannya untuk dikirim.
3
Digiman+ → Sistem Kalian
Digiman+ melakukan POST ke endpoint penerima kalian, berisi satu submission (bagian 3 & 4). Kalian membalas 2xx kalau berhasil diterima.
4
Sistem Kalian → Digiman+ (hanya jika perlu foto)
Untuk menampilkan/menyimpan foto, kalian meminta SAS token atas blob URL yang ada di payload (bagian 5), lalu mengambil file-nya langsung dari Azure Blob Storage — bukan lewat server Digiman+.
Kenapa push, bukan polling
Data sampai ke sistem kalian mendekati real-time — tidak perlu menunggu siklus polling berikutnya, dan tidak ada beban penjadwalan/paginasi di sisi kalian. Konsekuensinya: ketersediaan endpoint penerima kalian menjadi bagian penting dari integrasi. Kalau endpoint kalian sedang down, Digiman+ akan terus mencoba mengirim ulang (bagian 6) — tapi tidak ada mekanisme bagi kalian untuk "menarik" data yang terlewat, karena endpoint polling tidak lagi tersedia.

3. Endpoint yang Perlu Kalian Sediakan

Kalian menyediakan satu endpoint HTTP yang menerima kiriman submission dari Digiman+.

POST{endpoint penerima — ditentukan oleh kalian}
AspekKetentuan
MethodPOST
Content-Typeapplication/json; charset=utf-8
BodySatu objek submission — struktur lengkap di bagian 4. Bukan array, bukan dibungkus envelope.
Response suksesHTTP status 2xx apapun (mis. 200 atau 202). Body response tidak dibaca Digiman+.
Response gagalStatus 4xx atau 5xx — perlakuan retry-nya berbeda, lihat bagian 6.
AutentikasiMengikuti mekanisme yang kalian tentukan (mis. API key di header, Basic Auth, mTLS). Sampaikan ke tim Digiman+ saat provisioning — lihat 7.1.
TimeoutSampaikan ekspektasi waktu proses kalian. Disarankan endpoint membalas cepat (terima & antrikan), tidak menunggu seluruh proses internal selesai.
Wajib — endpoint harus idempotent
Digiman+ menerapkan at-least-once delivery: dalam kondisi tertentu (mis. response kalian hilang di jaringan setelah kalian selesai memproses) submission yang sama bisa terkirim lebih dari sekali. Endpoint kalian wajib menangani ini dengan upsert berdasarkan formSubmissionId, bukan insert baru — kalau tidak, data akan terduplikasi. Lihat bagian 6.2.

4. Payload Data Model

Struktur lengkap payload yang dikirim per submission:

{
  formSubmissionId, formCode, formVersion, formName, formSubGroup,
  siteCode, equipmentNumber,
  submittedBy, submittedAt, syncAt,
  tabs: [
    {
      title,
      sections: [
        {
          title,
          answers: [
            { taskCode, label, value, valueCode?, lastUpdatedBy, lastUpdatedAt,
              photos: [{ label?, url }], number?, remark? }
          ]
        }
      ]
    }
  ]
}

4.1 Perubahan Bentuk dari v0.4

Envelope dihapus
Di v0.4, objek submission berada di dalam array submissions[] bersama field paginasi. Sekarang objek submission adalah root dari body — hilangkan seluruh penanganan totalRecords/page/pageSize/hasMore/submissions[] dari parser kalian.

Penting — submittedAt bisa jauh lebih lama dari waktu kalian menerima data

Gunakan valueCode untuk logic, value untuk tampilan

Untuk item checklist inspeksi, jawaban dikirim dalam dua bentuk sekaligus:

FieldContoh isiPakai untuk
value"Ok" / "Not Ok"Ditampilkan ke pengguna, dicetak di laporan
valueCode"CONDITION_CHECK_OK" / "CONDITION_CHECK_NOTOK"Percabangan logic, filter, agregasi, hitung statistik

Alasannya: teks pada value adalah label tampilan yang dikelola lewat konfigurasi template form — sewaktu-waktu bisa diubah (mis. menjadi "OK", atau diterjemahkan). Kalau logic kalian membandingkan string value, perubahan label semacam itu akan membuat logic kalian rusak tanpa error yang jelas. valueCode jauh lebih stabil.

Catatan: nilai kode di atas berlaku untuk checklist kategori IIR. Kategori/varian form lain bisa memakai himpunan kode yang berbeda — perlakukan valueCode sebagai nilai yang dibaca dari payload, bukan daftar tetap yang di-hardcode.

Catatan bentuk value
  • Jawaban pilihan (item checklist "Ok"/"Not Ok") → string teks tampilan, disertai valueCode
  • Jawaban teks bebas (mis. nama inspector, SMU, catatan) → string biasa, tanpa valueCode
  • Jawaban yang isinya murni foto (mis. "Photo Machine SMU", "Foto Kondisi Fisik Equipment", tanda tangan digital) → value selalu null terlepas dari jumlah foto — seluruh fotonya ada di photos[]
  • Jawaban dengan foto sebagai lampiran tambahan (item checklist yang dijawab "Ok"/"Not Ok" lalu opsional dilampiri foto) → value tetap berisi jawaban utamanya, foto tetap terpisah di photos[]

5. Akses Foto — Blob URL & SAS Token

Foto tidak ikut dikirim di dalam payload — yang dikirim hanya URL-nya. Ini menjaga ukuran payload tetap wajar, karena satu submission inspeksi lengkap bisa memuat puluhan hingga ratusan foto.

URL pada photos[].url menunjuk langsung ke Azure Blob Storage, tapi tidak bisa diakses tanpa SAS token. Alurnya:

1
Kumpulkan blob URL yang ingin diakses dari payload (boleh banyak sekaligus).
2
Minta SAS token ke Digiman+ lewat endpoint di bawah (satu request bisa memuat banyak URL).
3
Ambil file langsung dari Azure Blob Storage memakai sasUrl yang diterima.

5.1 Request SAS Token

POST/form-submissions/photos/sas-token

Endpoint ini disediakan Digiman+. Autentikasinya memakai API Key + IP whitelist (bagian 7.2).

Contoh Request
POST /api/v1/form-submissions/photos/sas-token
X-Api-Key: {api_key}
Content-Type: application/json

{
  "urls": [
    "https://{storage}.blob.core.windows.net/{container}/evidence/1ccac17f-....jpg",
    "https://{storage}.blob.core.windows.net/{container}/evidence/8ffc591c-....jpg"
  ]
}

Kirim nilai photos[].url apa adanya seperti yang kalian terima di payload — tidak perlu diproses/dipotong.

Contoh Response — 200 OK
{
  "tokens": [
    {
      "url": "https://{storage}.blob.core.windows.net/{container}/evidence/1ccac17f-....jpg",
      "sasUrl": "https://{storage}.blob.core.windows.net/{container}/evidence/1ccac17f-....jpg?sv=2024-11-04&sr=b&sp=r&se=2026-08-20T10%3A00%3A00Z&sig={signature}",
      "sasToken": "sv=2024-11-04&sr=b&sp=r&se=2026-08-20T10%3A00%3A00Z&sig={signature}",
      "expiresAt": "2026-08-20T10:00:00Z",
      "error": null
    },
    {
      "url": "https://{storage}.blob.core.windows.net/{container}/evidence/8ffc591c-....jpg",
      "sasUrl": null,
      "sasToken": null,
      "expiresAt": null,
      "error": "URL_NOT_RECOGNIZED"
    }
  ]
}

5.2 Ketentuan

AspekKetentuan
BatchSatu request boleh memuat banyak URL sekaligus. Disarankan meminta token secara batch, bukan satu request per foto
Urutan hasilArray tokens mengikuti urutan array urls pada request — item ke-N berkorespondensi dengan item ke-N
Kegagalan sebagianURL yang gagal tidak membatalkan seluruh batch — item tersebut tetap muncul dengan sasUrl: null dan error terisi, sementara URL lain tetap mendapat token
Masa berlaku token24 jam sejak diterbitkan, ditunjukkan oleh expiresAt
Cara pakaiGunakan sasUrl (URL + token sudah tergabung) untuk GET langsung ke Azure Blob Storage. Field sasToken disediakan terpisah bagi yang ingin menyusun sendiri (mis. lewat Azure SDK)
Rekomendasi — minta token saat akan dipakai
Karena token berlaku 24 jam, mintalah SAS token pada saat foto benar-benar akan diambil/ditampilkan, bukan langsung saat payload diterima. Kalau kalian meminta token untuk semua foto di awal lalu baru memprosesnya beberapa hari kemudian, token sudah kedaluwarsa dan harus diminta ulang. Blob URL di payload sendiri tidak kedaluwarsa — aman disimpan permanen; yang berumur pendek hanya token-nya.
Caching
Isi foto bersifat immutable — satu blob URL tidak akan pernah berubah isinya. Setelah file berhasil diunduh, aman disimpan/di-cache di sisi kalian tanpa perlu mengunduh ulang, meskipun submission yang sama terkirim ulang (lihat 6.2).

6. Retry, Idempotensi & Urutan Pesan

6.1 Perilaku Retry Digiman+

Kalau pengiriman ke endpoint kalian gagal, Digiman+ akan mencoba ulang. Perlakuannya berbeda tergantung jenis kegagalan:

Respons kalianDitafsirkan sebagaiPerilaku Digiman+
2xxBerhasilSelesai, tidak dikirim ulang
5xx, timeout, koneksi gagalGangguan sementaraRetry terus-menerus dengan jeda yang meningkat bertahap, sampai berhasil. Data tidak hilang meski endpoint kalian down cukup lama
4xxKiriman ditolak permanenDihentikan & ditandai untuk ditinjau tim Digiman+, karena mengulang kiriman yang sama tidak akan mengubah hasil
Penting — jangan membalas 4xx untuk gangguan sementara
Kalau sistem kalian sedang bermasalah secara sementara (database down, antrian penuh, dependency internal tidak tersedia), balaslah 5xx, bukan 4xx. Balasan 4xx ditafsirkan sebagai "kiriman ini ditolak dan tidak perlu diulang" sehingga pengiriman dihentikan — submission tersebut tidak akan datang lagi dengan sendirinya, dan pemulihannya perlu koordinasi manual dengan tim Digiman+. Gunakan 4xx hanya kalau payload-nya sendiri memang tidak bisa kalian terima.

6.2 Idempotensi — Wajib Upsert by formSubmissionId

Integrasi ini bersifat at-least-once: submission yang sama bisa terkirim lebih dari sekali. Penyebab paling umum bukan kegagalan di sisi kalian, melainkan hal-hal seperti response yang hilang di jaringan setelah kalian selesai memproses — dari sisi Digiman+ itu terlihat seperti gagal, sehingga dikirim ulang.

Yang perlu kalian lakukan
Perlakukan formSubmissionId sebagai primary key di sisi kalian. Saat menerima kiriman:
  • Kalau formSubmissionId belum ada → simpan sebagai record baru
  • Kalau sudah ada → perbarui record yang ada (atau abaikan kalau isinya identik), jangan membuat record baru
Balas 2xx di kedua kasus — kiriman duplikat bukan error.

6.3 Urutan Pesan & Pembaruan Submission

Sebuah submission dapat dikirim ulang bukan hanya karena retry, tapi juga karena datanya diperbarui (mis. inspector menambahkan catatan atau foto setelah submit awal). Karena pengiriman berlangsung asinkron, urutan tiba tidak dijamin — pada kasus jarang, versi lama bisa tiba setelah versi baru.

Rekomendasi — pakai syncAt sebagai watermark
Simpan syncAt dari kiriman terakhir yang kalian proses untuk setiap formSubmissionId. Saat menerima kiriman untuk ID yang sama, bandingkan: kalau syncAt yang baru datang lebih lama dari yang tersimpan, abaikan (tetap balas 2xx) — itu versi usang. Dengan begitu data terbaru tidak akan tertimpa data lama.

6.4 Tidak Ada Endpoint untuk Menarik Data

Konsekuensi model push
Karena endpoint polling tidak dikembangkan (lihat 1.1), tidak ada cara bagi sistem kalian untuk menarik ulang data secara mandiri — baik untuk rekonsiliasi berkala ("apakah saya sudah menerima semua submission minggu ini?") maupun untuk mengambil ulang submission yang gagal kalian proses setelah membalas 2xx.

Implikasi praktis untuk desain sisi kalian:

  • Balas 2xx hanya setelah data benar-benar tersimpan aman (mis. sudah masuk database atau antrian yang persisten) — bukan sekadar setelah diterima di memori. Setelah 2xx, tanggung jawab data sepenuhnya ada di sisi kalian.
  • Kalau terjadi kehilangan data di sisi kalian, pengiriman ulang harus dikoordinasikan manual dengan tim Digiman+.

7.1 Kredensial untuk Endpoint Kalian

Digiman+ akan mengikuti mekanisme autentikasi yang kalian tentukan. Saat provisioning, sampaikan ke tim Digiman+:

  • URL endpoint penerima (staging dan production)
  • Mekanisme autentikasi dan kredensialnya (mis. nama header + API key, Basic Auth, atau sertifikat mTLS)
  • Ekspektasi timeout dan batasan lain yang relevan (mis. ukuran payload maksimum yang bisa kalian terima)

7.2 API Key untuk Endpoint SAS Token

Untuk memanggil endpoint SAS token (bagian 5), kalian menerima 1 API Key statis dari Digiman+. Autentikasinya dua faktor: API Key harus valid, dan request harus berasal dari IP yang sudah didaftarkan.

Sertakan API Key di header:

X-Api-Key: {api_key}

Sebelum integrasi dimulai, sampaikan IP/CIDR range asal request (egress IP sistem kalian) untuk didaftarkan ke whitelist. Simpan API Key dengan aman (mis. secret manager) — jangan di-commit ke source control atau di-log.

Penting
Request dengan API Key valid tapi berasal dari IP di luar whitelist akan tetap ditolak (403). Kalau IP/infrastruktur sistem kalian berubah (mis. pindah data center, ganti provider cloud), segera informasikan ke tim Digiman+ untuk update whitelist — request dari IP baru yang belum terdaftar akan gagal sampai whitelist diperbarui.

8. Best Practices Integrasi

  • Buat endpoint penerima idempotent sejak awal — upsert by formSubmissionId. Ini bukan optimasi, tapi keharusan: duplikat pasti terjadi cepat atau lambat (lihat 6.2).
  • Balas cepat, proses belakangan — terima payload, simpan ke storage/antrian persisten, balas 2xx, lalu proses secara asinkron. Endpoint yang menahan response sampai seluruh proses internal selesai berisiko timeout dan memicu pengiriman ulang yang tidak perlu.
  • Balas 2xx hanya setelah data tersimpan aman — setelah itu tidak ada mekanisme otomatis untuk mengirim ulang (lihat 6.4).
  • Gunakan 5xx untuk gangguan sementara, 4xx hanya untuk penolakan permanen — salah memilih akan menghentikan pengiriman ulang yang seharusnya terjadi (lihat 6.1).
  • Simpan syncAt sebagai watermark per submission untuk menangkal kiriman versi usang (lihat 6.3).
  • Pakai valueCode untuk logic, bukan value — teks tampilan bisa berubah sewaktu-waktu (lihat 4.4).
  • Jangan hardcode nama tab/section — iterate secara dinamis (lihat 4.3). Ini yang membuat penambahan kategori form baru tidak memerlukan perubahan kode di sisi kalian.
  • Handle photos[].url: null secara graceful — jangan sampai satu foto gagal membuat seluruh submission gagal diproses.
  • Minta SAS token secara batch dan saat akan dipakai — bukan satu request per foto, dan bukan di muka untuk semua foto (lihat 5.2).
  • Simpan blob URL, bukan sasUrl — blob URL permanen, sedangkan sasUrl kedaluwarsa dalam 24 jam.
  • Perhatikan bahwa submittedAt bisa jauh lebih lama dari waktu terima — akibat pengisian offline (lihat 4.2).

9. Versioning & Change Policy

Versi API Digiman+ (endpoint SAS token) ada di URL path (/api/v1/...). Kebijakan perubahan:

  • Breaking change (hapus/rename field, ubah tipe data, ubah semantik) → rilis versi baru (/v2), versi lama tetap berjalan selama masa transisi
  • Non-breaking change (tambah field baru yang opsional) → tidak mengubah versi, aman untuk integrasi existing
  • Masa transisi/deprecation — versi lama tidak langsung dimatikan; notifikasi dan window waktu akan diberikan sebelum versi lama disunset
Penambahan field pada payload
Digiman+ dapat menambahkan field baru pada payload di kemudian hari tanpa menaikkan versi. Pastikan parser kalian toleran terhadap field yang tidak dikenal (abaikan, jangan error) — ini praktik standar dan mencegah integrasi kalian rusak oleh penambahan yang sebenarnya aman.
