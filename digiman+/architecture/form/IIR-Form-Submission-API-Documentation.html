1. Overview & Perubahan dari v0.3

API ini menyediakan akses read-only ke data hasil pengisian form self-service di Digiman+ — form yang diisi lewat menu mobile "Form Submission" (bukan form inspeksi/PM/BD corrective terjadwal). Model aksesnya adalah pull/polling — sistem eksternal yang menarik data secara berkala (bukan webhook/push dari Digiman+).

IIR (Inspection Report) adalah kasus pemakaian awal yang mendorong desain endpoint ini, tapi endpoint-nya tidak dikunci ke IIR saja — form self-service dikelompokkan jadi beberapa kategori (mis. IIR), dan endpoint ini bisa melayani kategori form lain di masa depan cukup dengan mengganti nilai parameter formSubGroup di request kalian — tidak perlu endpoint baru tiap kali ada kategori form tambahan.

Setiap submission mencakup metadata (kategori form, site, equipment, waktu submit) dan seluruh jawaban form (termasuk foto, terstruktur per tab & section).

1.1 Ringkasan Perubahan dari Draft v0.3

Breaking changes — perlu penyesuaian di sisi integrasi kalian
  • URL endpoint berubah: /iir-form-submissions → /form-submissions (termasuk endpoint download foto)
  • Mekanisme autentikasi berubah: dari OAuth2 Client Credentials Grant (Bearer token) → API Key + IP whitelist, disamakan dengan pola integrasi eksternal lain (mis. SAP) — lihat 2
  • Parameter baru wajib: formSubGroup — request tanpa parameter ini sekarang invalid (lihat 3.1 & 6.3)
  • Parameter siteCode sekarang wajib (sebelumnya opsional) — request tanpa siteCode sekarang invalid (lihat 3.1 & 6.4)
  • Field baru di response: formSubGroup — muncul di setiap objek submission (lihat 4.2)
  • Field taskCode sekarang selalu ada di kedua tab ("General" maupun "Inspection") — sebelumnya cuma ada di tab "Inspection" (lihat 4.4)
Non-breaking — aman untuk integrasi existing
  • equipmentNumber sekarang boleh diisi lebih dari satu nilai (comma-separated) — kalau kalian sudah pakai satu nilai, tetap jalan seperti biasa (lihat 6.4)
  • Error code baru MISSING_REQUIRED_PARAMETER untuk kasus formSubGroup/siteCode tidak diisi (lihat 8)
  • Angka rate limit endpoint download foto direvisi (lihat 7.2) — masih estimasi, belum final

Base URL

https://{host}/api/v1

Placeholder — domain final (staging/production) akan diinformasikan terpisah sebelum go-live.

2. Autentikasi

Autentikasi pakai API Key + IP whitelist — pola yang sama dengan integrasi sistem eksternal lain di Digiman+ (mis. SAP). Kedua faktor dicek bersamaan: API Key harus valid, dan request harus datang dari IP yang sudah didaftarkan untuk key tersebut.

2.1 Provisioning

Sebelum integrasi dimulai, kalian akan diminta menyampaikan ke tim Digiman+:

  • IP/CIDR range asal request (egress IP sistem kalian) untuk didaftarkan ke whitelist

Sebagai balasannya, kalian akan menerima 1 API Key statis per integrasi. Simpan API Key ini dengan aman (mis. secret manager) — jangan di-commit ke source control atau di-log.

2.2 Pakai API Key

Sertakan API Key di header berikut pada setiap request ke endpoint data maupun endpoint foto:

X-Api-Key: {api_key}
Penting
Request dengan API Key valid tapi berasal dari IP di luar whitelist akan tetap ditolak (403 FORBIDDEN, lihat 8). Kalau IP/infrastruktur sistem kalian berubah (mis. pindah data center, ganti provider cloud), segera informasikan ke tim Digiman+ untuk update whitelist — request dari IP baru yang belum terdaftar akan gagal sampai whitelist diperbarui.

2.3 Scope Akses

API Key yang valid otomatis punya akses ke semua site — tidak ada pembatasan akses per site. Parameter formSubGroup/siteCode/equipmentNumber pada request murni untuk menyaring hasil pencarian, bukan kontrol keamanan.

4. Response Data Model

Struktur lengkap response (baik dari endpoint list maupun single-fetch):

{
  dateFrom, dateTo,              // hanya di endpoint list — echo balik parameter request
  totalRecords, page, pageSize, hasMore,   // hanya di endpoint list
  submissions: [                 // hanya di endpoint list — endpoint single-fetch return submission langsung
    {
      formSubmissionId, formCode, formVersion, formName, formSubGroup,
      siteCode, equipmentNumber,
      submittedBy, submittedAt, syncAt,
      tabs: [
        {
          title,
          sections: [
            {
              title,
              answers: [
                { taskCode, label, value, lastUpdatedBy, lastUpdatedAt, photos: [{ label?, url }], number?, remark? }
              ]
            }
          ]
        }
      ]
    }
  ]
}

Wajib di-handle
Kalau photos[].url bernilai null, artinya foto tersebut ada tapi gagal di-resolve saat request diproses. Jangan asumsikan selalu berisi URL valid — tampilkan placeholder/skip, jangan sampai integrasi gagal total karena satu foto null. Kalau url terisi tapi endpoint 3.3 mengembalikan 404 saat dipanggil, treat sama seperti null (foto tidak tersedia). Kasus null ini bisa lebih sering muncul di awal go-live selagi data foto lain di sisi Digiman+ masih dirapikan — desain graceful-handling ini sengaja disiapkan untuk itu.

5. Pagination

Endpoint list (3.1) selalu dipaginasi. Default pageSize adalah 20, maksimal 100.

Loop paginasi standar:

page = 1
loop:
  response = GET /form-submissions?dateFrom=...&dateTo=...&formSubGroup=IIR&siteCode=LAT&page={page}&pageSize=100
  process(response.submissions)
  if response.hasMore == false:
    break
  page += 1

totalRecords merepresentasikan total submission yang match filter di semua halaman, bukan cuma halaman berjalan.

6. Filtering & Panduan Polling

6.1 Rentang Tanggal — Maksimal 7 Hari

dateFrom/dateTo wajib diisi, dan jarak antara keduanya maksimal 7 hari. Kalau butuh rentang lebih panjang, pecah jadi beberapa request berurutan.

6.2 submittedAt vs syncAt — Kenapa Bisa Beda

Digiman+ mendukung pengisian form secara offline di lapangan. Karena itu ada 2 timestamp dengan makna berbeda:

  • submittedAt — waktu inspector menyelesaikan form di device. Bisa terjadi saat device offline.
  • syncAt — waktu data tersebut benar-benar tersedia di server (setelah device online dan sync). Bisa lebih lambat dari submittedAt — kadang beda beberapa menit, kadang beda beberapa hari kalau device lama offline.
Implikasi Penting
Filter dateFrom/dateTo pada endpoint list berdasarkan syncAt, bukan submittedAt. Jadi wajar kalau suatu submission dengan submittedAt beberapa hari yang lalu baru muncul di hasil polling hari ini — itu karena device-nya baru online dan sync hari ini. Desain ini memastikan sistem eksternal tidak pernah kehilangan data akibat keterlambatan sync, asalkan window polling mencakup waktu syncAt-nya.

Rekomendasi polling: jalankan polling secara berurutan tanpa celah (mis. window kemarin berakhir jam 23:59:59, window hari ini mulai jam 00:00:00) — cukup andalkan syncAt, tidak perlu overlap manual di sisi sistem eksternal.

6.3 Kategori Form — formSubGroup (Wajib) Baru

Form self-service di Digiman+ dikelompokkan jadi beberapa kategori — IIR adalah salah satu kategori yang tersedia. Parameter formSubGroup wajib diisi, tepat satu nilai per request — tidak ada mode "ambil semua kategori sekaligus".

Alasan wajib & satu nilai: struktur tab/section/jawaban antar kategori form bisa sangat berbeda — mencampur beberapa kategori dalam satu response berisiko membingungkan sisi parsing kalian. Dengan mewajibkan satu nilai eksplisit, integrasi kalian selalu tahu persis kategori apa yang sedang diproses.

Untuk masa depan
Kalau Digiman+ menambah kategori form baru, kalian cukup mengganti nilai formSubGroup di request (setelah dikomunikasikan nilai kategorinya) — tidak perlu perubahan endpoint atau kode integrasi di sisi kalian.

6.4 Filter Site & Equipment

siteCode wajib diisi, tepat satu nilai — sejajar dengan formSubGroup, bukan filter opsional.

equipmentNumber tetap opsional, dan sekarang boleh diisi lebih dari satu nilai sekaligus (dipisah koma):

equipmentNumber=HDCT73112,HDCT73113

Kosong/tidak diisi = semua equipment di site & kategori yang diminta akan ikut ke-return. Di response, equipmentNumber tetap muncul sebagai satu nilai per submission (lihat 4.2) — multi-value hanya berlaku di parameter filter request, bukan bentuk data submission itu sendiri.

7. Rate Limiting

Rate limit berlaku per API Key (bukan per IP asal request — IP dipakai untuk whitelist gate, bukan unit kuota). Kuota terpisah antara endpoint data dan endpoint download foto — karakteristik beban keduanya beda jauh (query data vs stream file).

7.1 Endpoint Data (3.1 List, 3.2 Get by ID)

WindowLimit
Per menit30 request
Per hari2.500 request

Limit ini cukup longgar untuk pola polling berkala maupun paginasi banyak halaman — kira-kira 1 request tiap 2 detik.

7.2 Endpoint Download Photo (3.3)

WindowLimit
Per menit1.850 request
Per hari155.000 request

Limit jauh lebih longgar karena 1 submission bisa punya puluhan hingga ratusan foto sekaligus (checklist inspeksi lengkap). Angka ini masih estimasi berbasis worst-case dan bisa direvisi sebelum go-live — kalau butuh throughput lebih tinggi dari ini, hubungi tim Digiman+.

Saat Limit Terlampaui

HTTP/1.1 429 Too Many Requests
Retry-After: 12

{
  "error": {
    "code": "RATE_LIMITED",
    "message": "Rate limit exceeded, retry after 12 seconds",
    "details": null
  }
}

Gunakan header Retry-After (dalam detik) untuk menentukan kapan retry, dan monitor header X-RateLimit-Remaining di setiap response supaya bisa self-throttle sebelum kena limit.

8. Error Handling

Semua error mengikuti format envelope yang sama:

{
  "error": {
    "code": "DATE_RANGE_TOO_LARGE",
    "message": "Date range exceeds maximum of 7 days",
    "details": null
  }
}

code adalah string machine-readable — gunakan ini untuk branching logic, jangan parsing message (yang human-readable dan bisa berubah). details nullable, dipakai untuk kasus validasi dengan lebih dari satu field bermasalah (array of {field, reason}).

9. Best Practices Integrasi

  • Selalu kirim formSubGroup dan siteCode secara eksplisit — keduanya wajib, request tanpa keduanya akan ditolak dengan MISSING_REQUIRED_PARAMETER.
  • Selalu loop sampai hasMore: false — jangan asumsikan semua data selalu muat di 1 halaman.
  • Jangan hardcode nama tab/section — iterate tabs/sections/answers secara dinamis (lihat catatan di 4.3), terutama kalau integrasi kalian nanti dipakai untuk kategori form (formSubGroup) selain IIR juga.
  • Handle photos[].url: null dengan graceful — jangan sampai 1 foto gagal resolve membuat seluruh proses integrasi gagal.
  • Simpan formSubmissionId + syncAt sebagai watermark untuk tracking data yang sudah diproses, memudahkan dedup kalau ada request yang di-retry.
  • GET bersifat idempotent — aman untuk retry otomatis kalau request gagal karena masalah jaringan (bukan karena error 4xx).
  • Terapkan exponential backoff saat menerima 429, hormati header Retry-After.
  • Gunakan endpoint single-fetch (3.2) untuk retry granular — kalau 1 submission gagal diproses dari hasil polling, tidak perlu re-poll seluruh rentang tanggal, cukup fetch ulang submission tersebut by ID.

10. Versioning & Change Policy

Versi API ada di URL path (/api/v1/...). Kebijakan perubahan:

  • Breaking change (hapus/rename field, ubah tipe data, ubah semantik filter) → rilis versi baru (/v2), versi lama tetap berjalan selama masa transisi
  • Non-breaking change (tambah field baru yang opsional, tambah endpoint baru) → tidak mengubah versi, aman untuk konsumen existing
  • Masa transisi/deprecation — versi lama tidak langsung dimatikan; notifikasi dan window waktu akan diberikan sebelum versi lama disunset
